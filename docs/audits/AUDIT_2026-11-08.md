## Findings

### H1 — High — A Test APK's update button downloads the Release APK, which cannot install over it

- **Where:** `app/lib/features/app_update/data/app_update_providers.dart:23-27` and `:29-37`
  (`testApkServeUrl` → `https://<domain>/app`), `app/lib/features/app_update/data/test_release_source.dart:66`
  (`downloadUrl: serveUrl.isEmpty ? apk : serveUrl`), `deploy/fetch_test_apk.sh:18-23` and `:32`.
- **What is wrong:** #265 made every Test APK send its user to `https://<domain>/app`. #270 made the same
  file (`/srv/bagmitra-apk/bagmitra.apk`) the Release APK when `RELEASE_APK_MIRROR=on`, and from then on the
  test mirror never writes it again (`release-code` exists → exit). The Test APK still finds newer test
  builds on GitHub (code 157 today) and shows the update notice, but the button downloads the Release APK:
  release key (not the test key) and version code 1 (the Release workflow's run number). Android refuses
  it ("App not installed": different signature, lower version code), and the notice comes back every
  6 hours.
- **Evidence:** code citations above; GitHub releases today: `release-1.0.0-1` "BagMitra 1.0.0 (version
  code 1)" and test builds up to "· code 157" (REST `GET /repos/…/releases`). `release-apk.yml:86`
  (`code="${{ github.run_number }}"`) vs `release-test-apk.yml:65` (`BUILD_NUMBER: ${{ github.run_number }}`
  of its own workflow). Whether `RELEASE_APK_MIRROR=on` is set on the VPS is not known (not read; owner rule
  A.2); the finding applies as soon as it is.
- **Rule broken:** owner request #265 (testers update from our own address) and runbook `test-apk.md`
  (a test build installs only test-key builds; audit BG-07 in `app_update_providers.dart:11-12`).
- **Smallest fix:** keep the two channels in two files: the test channel always writes
  `bagmitra-test.apk` served at `/app/test` (the release channel keeps `/app`), and `testApkServeUrl`
  returns `<origin>/app/test`. Until then, Test APKs should use the GitHub asset URL.

### M1 — Medium — Feedback: the app allows 2000 letters, the API allows 2000 code points

- **Where:** `app/lib/features/feedback/presentation/feedback_screen.dart:87` (`maxLength: 2000`);
  `api/src/bagmitra_api/routers/feedback.py:39` (`Field(min_length=1, max_length=2000)`).
- **What is wrong:** Flutter's `maxLength` counts grapheme clusters
  (`flutter/lib/src/services/text_formatter.dart:543,567` use `text.characters.length`); pydantic counts
  code points. Marathi letters with a vowel sign or a conjunct are 2–3 code points (`कि` = 2, `क्ष` = 3),
  so a long Marathi (or voice-typed) message that the app accepts is refused with 422.
- **Evidence:** `test_f1_a_2000_letter_marathi_message_is_accepted`: `"कि" * 2000` → `422
  validation_error` (expected 201).
- **Rule broken:** feedback spec #257/#258 (any message the screen accepts is sent).
- **Smallest fix:** raise the API limit to 8000 (worst case 4 code points per letter) or count
  graphemes on the server; keep the app's 2000.

### M2 — Medium — Feedback outbox: one refused message blocks every later message forever

- **Where:** `app/lib/features/feedback/data/feedback_outbox.dart:150-163` (`if (!await
  _server.send(d)) break;`), `:73` (`return res.isSuccessful;`).
- **What is wrong:** `flush` stops at the first message the server does not accept and keeps it first in
  the queue. A permanent refusal (422 from M1, 409 `feedback_id_taken`) is treated like "offline", so that
  message and every message written after it are never sent, while the user is told "saved on the phone;
  it will go when online".
- **Evidence:** `app/test/zz_audit_repro_test.dart`: first message refused, two later messages → `Expected: ['second message', 'third message']  Actual: []`.
- **Rule broken:** offline queue (#258: "feedback written offline goes once the app starts online").
- **Smallest fix:** `send` returns sent / retry-later / refused; on refused (4xx other than 429) drop the
  draft (or move it aside) and continue with the next.

### M3 — Medium (owner decision) — Turning the switch OFF (or clearing a role's amount) hides the subscription page from users Play keeps charging

- **Where:** `api/src/bagmitra_api/routers/billing.py:126-132` (`role` is None unless the switch is in
  force, so `covered` is False); `app/lib/app/providers.dart:517-521` (startup reconcile only when
  `inForce || covered`); `app/lib/features/more/presentation/more_screen.dart:27-30` (entry only when
  `showsPlan || covered || priceChange`).
- **What is wrong:** a user who subscribed while the switch was ON keeps an ACTIVE, auto-renewing Play
  subscription after the admin turns the switch OFF (or empties that role's amount); nothing cancels it.
  From then on `/v1/billing/plan` answers `covered: false`, the app no longer shows "सदस्यता" with its
  "सदस्यता व्यवस्थापन" link, and the app stops re-sending the token at start. The user is charged every
  month for features everyone gets free, with no path in the app to cancel.
- **Evidence:** `test_f3_…`: ON → buy → `covered: true`; OFF → `{"covered": false, "in_force": false, …}`
  while the Play subscription is still ACTIVE.
- **Rule broken:** spec §7 does not say what happens to existing subscribers at OFF; addendum §2.3 requires
  a Manage-subscription link for subscribers.
- **Smallest fix (after the owner decides):** `covered` = "the user holds an active Play role
  subscription", independent of the switch, so the page and Manage link stay; plus the owner's choice of
  what OFF means for payers (leave them, or tell them in the app to cancel in Play).

### M4 — Medium — Spec §7, ADR 0008 and the admin page state a wrong Play rule for price decreases

- **Where:** `docs/SPEC_billing_addendum.md` §7 ("a decrease reaches existing subscribers at their next
  payment"); `docs/adr/0008-billing-play.md` fact 3; `app/lib/admin/billing_strings.dart:46,83,119`
  (`rule_down`).
- **What is wrong:** Google's current page (developer.android.com/google/play/billing/price-changes,
  re-read 2026-11-08) says existing subscribers stay in a legacy price cohort for a decrease too; they pay
  the lower price only after the developer ends the cohort (`basePlans.migratePrices`). The admin is told
  a decrease reaches subscribers by itself, so after lowering an amount nobody would run "Move existing
  subscribers" and current subscribers keep paying the old, higher price.
- **Evidence:** Google page: decreases are not automatic; subscribers start paying the lower price "the
  next time they pay" only when the cohort is ended. The code's migration call itself is correct
  (`play.py:160-182`).
- **Rule broken:** spec §7 "Price changes for existing subscribers follow Play's rules, shown on the admin
  page before saving".
- **Smallest fix:** correct the sentence in the spec, the ADR and `rule_down` (all three languages): "a
  lower price reaches existing subscribers only after 'Move existing subscribers'; then from their next
  payment".

### M5 — Medium — Data Safety and DATA_INVENTORY not updated for Play subscriptions and feedback

- **Where:** `docs/legal/DATA_INVENTORY.md:110` (Payments: "subscriptions are manual grants (`provider`

- **Rule broken:** task rule "DATA_INVENTORY updated for new data"; Play Data Safety must match what is

- **Smallest fix:** update DI:110 to the stored Play fields; in `data-safety.md` add feedback (App activity →

### M6 — Medium (suspected; not verifiable without Google) — The daily voided-purchases poll asks for exactly 30 days back

- **Where:** `api/src/bagmitra_api/billing/reconcile_job.py:40,61` (`now - VOIDED_WINDOW`, 30 days);

  @override
  Future<bool> send(FeedbackDraft d) async {

    sent.add(d.text);
    return true;
  }

  @override
  Future<bool> sendScreenshot(String id, List<int> jpeg) async => true;
}

    final db = memoryDb();
    addTearDown(db.close);
